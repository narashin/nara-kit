# 게시 계약 — 판정을 PR에 올릴 때

이 문서는 두 곳이 함께 쓴다. `nara-pr-review`의 게시 단계, 그리고 판정이 나온 뒤 사람이 게시를 요청했을 때 도는 별도 실행. 규칙을 양쪽에 복사해두면 한쪽만 바뀌어 갈라지므로 여기 하나로 둔다.

후자의 제스처 계약은 [card-gestures](../../nara-review-queue/references/card-gestures.md)에 있다. **그 파일이 없으면 무시하고 진행한다** — 게시 규칙은 이 문서로 완결되고, 저쪽은 트리거(`/ask` `/post` `/approve`)와 상태 전이만 다룬다. 헤드리스 실행에서는 이 스킬만 워크트리에 복사되므로 그 링크는 열리지 않는 것이 정상이다.

이 파일이 없으면 게시하지 않는다. 다음 세 줄만 지키고 나머지는 사람에게 묻는다: 지적 내용을 바꾸지 말 것, 리뷰 하나로 게시할 것, approve는 사람이 명시했을 때만.

## 승인 게이트

게시는 **사람이 명시적으로 요청한 것만** 한다. 판정이 나왔다는 사실은 게시 승인이 아니다.

`approve` / `request-changes` verdict는 항상 사람 몫이다. `status: pass`에서 approve를 유도하지 않는다. 머지 신호이기 때문이다.

사람이 approve를 요청했을 때 그게 허용되는지는 **판정문의 기계 필드로 판정한다.** 산문을 읽고 "수정을 요구하는 것 같다"로 거부하지 않는다.

| 판정 | approve |
|---|---|
| `status: pass` + `blocking: 0` | 게시한다. 비차단 지적(suggestion·test-gap)은 지우지 말고 본문에 남긴다 (아래 "본문 형태") |
| `blocking: 1` 이상 또는 `status: changes_requested` | 거부하고 이유를 보고한다. 코멘트로만 올리는 것은 별개 제스처다 |
| `status: blocked` | 거부한다. 리뷰가 수행되지 않은 판정이라 approve할 근거가 없다 |

`blocking: 0`인데 summary가 "주석 보정과 회귀 테스트가 필요하다"로 끝나는 것은 approve-with-nits의 정상 모양이다. 그 문장을 수정 요구로 읽어 거부하면 비차단 지적만 있는 PR은 영구히 approve되지 못한다. 실측으로 그랬다. 같은 판정에 approve를 하루 간격으로 두 번 요청했고 두 번 같은 이유로 거부됐다.

거부가 판정문에서 기계적으로 도출된다면 **게시 세션을 띄우기 전에** 결정한다. 워크트리와 세션을 태워서 도달할 결론이 아니다.

## 언어

리포트와 판정문은 한국어로 쓴다. 하지만 **게시 코멘트는 대상 repo의 언어 관행을 따른다.** `gh pr view`의 본문과 기존 코멘트로 확인한다. 영어 repo에 한국어 리뷰를 올리지 않는다.

## 다시 쓰기

판정문은 보드용으로 쓰인 글이라 그대로 내보내면 안 된다. 걷어낼 것:

- 기계용 헤더 — `status:`, `blocking:`, `suggestion:`, `test-gap:` 카운트 줄
- 내부 문구 — "PR에는 게시하지 않았다", "사람이 정한다", "판정만 카드로 돌아온다"
- 트래커 언급 — 워크트리 이름, 카드 번호, 큐 상태

유지할 것:

- 지적의 **내용·근거·심각도**. 없던 지적을 만들지 않고, 있는 지적을 빼지 않는다
- 코드 위치를 `파일:줄`로
- 차단성과 비차단성의 구분. 비차단 지적을 차단처럼 쓰지 않는다

## 본문 형태

첫 줄에 어느 모델이 리뷰했는지 밝힌다. 값은 카드 metadata의 `review_model`을 먼저 보고, 없으면 판정문 헤더의 모델 필드를 쓴다. 둘 다 없으면 그 줄을 생략하고 게시한다. **게시 세션 자신의 모델을 대신 적지 않는다.** 게시는 리뷰를 수행한 세션이 아니라서 그 값은 틀린 값이고, 얇은 판정을 무거운 모델이 본 것처럼 보이게 만든다.

**길이는 지적 수가 정한다. 그 밖의 것은 쓰지 않는다.** 리뷰를 받는 쪽은 자기 코드를 이미 알고 있으니 배경 설명이 필요 없고, 긴 코멘트일수록 정작 고쳐야 할 줄이 묻힌다.

- 서두와 맺음말을 쓰지 않는다. "리뷰 진행했습니다", "전반적으로 잘 작성되었습니다", "확인 부탁드립니다", "궁금한 점 있으면 말씀해 주세요"는 전부 뺀다. 첫 줄은 모델 고지이고 그다음은 바로 지적이다.
- 지적 하나는 한 문장이 기본이고, 근거가 필요하면 `파일:줄`을 붙여 두 문장까지다. 그보다 길어져야 하는 지적은 코멘트가 아니라 별도 논의 거리다.
- 이미 쓴 내용을 끝에서 다시 요약하지 않는다.
- 지적이 여섯 개를 넘으면 차단 항목을 먼저 다 쓰고, 비차단은 중요한 것부터 다섯 개까지만 남긴다. 나머지는 "이 밖에 사소한 것 N건은 생략했다"로 한 줄 처리한다. 열 개를 나열하면 아무것도 안 읽힌다.

차단성은 라벨이 아니라 문장으로 쓴다. `차단:` `비차단:` 같은 콜론 접두어를 항목 앞에 붙이지 않는다. 보드에서는 스캔용으로 쓸모가 있지만 PR에서는 사람이 읽는 글이고, 라벨은 지적을 통보처럼 들리게 한다. 차단 지적은 "Blocking 요소가 있습니다" 같은 문장으로 열고 내용을 잇는다. 비차단 지적은 차단 항목을 다 쓴 뒤 "Non-blocking 의견으로는 ..."으로 이어 붙인다. 지우지 않는다. 차단이 없으면 비차단만 같은 방식으로 쓴다.

본문을 다 쓰면 게시 전에 [nara-ko-prose](../../nara-ko-prose/SKILL.md)를 태운다. 조사·어미가 빠진 문장과 명사구로 끊긴 문장을 완결하는 것이 목적이다. **그 스킬이 없으면 건너뛰고 게시한다.** 영어 repo에서는 위 한국어 예시 대신 같은 취지의 영어 문장을 쓰고 이 단계를 건너뛴다.

## 게시 형태

```bash
gh pr review <번호> --repo <owner/repo> --comment  --body-file <파일>
gh pr review <번호> --repo <owner/repo> --approve  --body-file <파일>
```

`GH_HOST`를 PR URL의 hostname으로 export한 뒤에 호출한다. 안 하면 엔터프라이즈 PR도 github.com에서 찾다가 실패한다 ([pr-plane](pr-plane.md) 참고).

리뷰 **하나로** 게시한다. 인라인 코멘트를 개별로 흩뿌리지 않는다. 지적이 여러 개면 한 본문 안에서 구분한다.

## 금지

- 코드 수정·커밋·push·머지. 게시 실행은 게시 하나만 한다
- CI가 이미 잡은 문제를 finding으로 중복 게시
- 판정문에 없는 새 지적 추가
- 중복 게시. 성공한 뒤에는 다시 하지 않는다
