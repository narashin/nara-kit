# 증류 판정 루브릭 (digest 단계 전용)

입력은 큐에 누적된 항목 전체다 (대개 1주 안팎, 여러 repo). 항목 하나당 아래 4개 중 **정확히 하나**로 판정한다. 요약이 아니라 판정이 산출물이다 — 새로 나왔다는 알림은 watch 단계가 이미 보냈다.

누적 판정이므로 항목 단위 판정에 더해 **교차 repo 패턴**을 별도 섹션으로 올릴 수 있다: 여러 repo가 같은 기간에 같은 방향으로 움직인 것 (예: 둘 이상이 "거부 대신 라벨로 노출하고 사람이 판단" 쪽으로 이동). 패턴 섹션도 근거 항목의 repo·버전을 명시해야 하며, 단일 항목 4분류를 대체하지 않는다.

## 기본값은 `의존`

판정이 애매하면 `의존`이다. 이 잡은 구조상 "남이 만든 걸 계속 흡수하는 루프"이고, `의존`이 기본값이 아니면 매일 "이거 우리도 만들자" 후보만 쌓인다.

vendor-free는 **배포 산출물의 속성**이지 개인 워크플로의 목표가 아니다. nativize는 (1) 이식이 싸고 (2) nara-kit의 테제를 날카롭게 할 때만 정당하다. 둘 중 하나라도 아니면 그 툴을 그냥 쓴다.

## 4분류

### `이미 있음`

nara-kit이 이미 하는 일이다. **그 스킬 이름을 반드시 명시한다.** 이름을 못 대면 이 판정을 쓸 수 없다 — 못 대는 건 "겹치는 것 같다"는 인상이고, 인상으로 릴리즈를 버리면 진짜 새로운 것을 놓친다.

> `이미 있음` — 워크트리 자동 생성은 `nara-wt`가 `wt` 헬퍼로 이미 함. 차이 없음.

### `의존` (기본값)

그 툴을 그대로 쓰면 되는 것. 왜 흡수하지 않는지 한 줄로 쓴다.

> `의존` — MCP 서버로 붙이면 끝. 스킬로 감싸면 그쪽 업데이트를 따라가는 비용만 생긴다.

### `증류 후보`

nara-kit에 흡수할 값이 있는 것. 아래 3개를 **모두** 채워야 후보다. 하나라도 못 채우면 `의존`으로 내린다.

1. **어느 스킬에** — 새 스킬이 아니라 기존 스킬의 어느 스텝인지. 새 스킬이 필요하다고 판단하면 그 근거를 별도로 쓴다
2. **왜 직접 만드는 게 싼가** — 이식 비용 대비 의존 비용
3. **어떤 아이디어인가** — 코드가 아니라 계약·판정 기준·순서 중 무엇을 가져오는지

> `증류 후보` — `nara-code-review`의 verification 스텝에. 그쪽 "실패 케이스를 먼저 재현하고 통과를 증거로 쓰지 않는다"는 판정 순서가 우리 gate와 같은 문제를 다루는데 더 명시적임. 코드는 안 가져오고 순서만.

### `무시`

우리 문제가 아니다. 왜 아닌지 한 줄. 이 판정이 가장 많이 나오는 것이 정상이다.

> `무시` — Python 런타임 최적화. nara-kit은 워크플로 계약이지 실행 성능이 아님.

## 출력 형식

```markdown
# Release Digest — 2026-09-02 (큐 9건, 2026-08-26 ~ 09-02)

## obra/superpowers v3.0.0 → [증류 후보](url)

**어느 스킬에**: nara-code-review verification 스텝
**왜 싼가**: 판정 순서만 가져오면 됨. 코드 이식 없음
**아이디어**: 통과를 증거로 쓰지 않고 실패 재현을 먼저 요구하는 순서

## anthropics/claude-code v2.2.0 → 의존

hook 이벤트가 늘어난 것. 우리는 배선만 하면 되고 감쌀 표면이 없다.
```

`증류 후보`가 0건인 날은 그렇게 쓴다. 억지로 후보를 만들지 않는다.

## 판정하지 않는 것

- 큐에 없는 것 — digest는 "알린 것 중에서" 판정한다. `suppressed`(임계 미달)·`baselined`(첫 관측)·prerelease는 큐에 들어오지 않는다
- watch 단계 — 알림에는 판정을 싣지 않는다. 판정은 이 문서를 읽는 digest에서만
