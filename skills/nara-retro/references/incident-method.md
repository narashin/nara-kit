# skill-incident 진단 방법

skill-incident 모드에서 대상 스킬 하나와 사건 하나가 정해진 뒤에만 읽는다. 넓은 최적화가 아니라 원인을 가르는 진단이다. 출처: tiger-kit `tk-retro` `references/failure-planes.md`·`empirical-method.md` (`5e633e3`), 증류해 줄였다.

## 실패 평면

문구 결함부터 가정하지 않는다. 증상마다 증거가 있는 평면에 대응시킨다.

| 평면 | 뜻 | 대표 증거 |
|---|---|---|
| 선택 | 필요 없는데 골랐거나, 필요한데 안 골랐다 | 고른 스킬, description 트리거 |
| 로딩 | 골랐지만 본문이 안 실렸다 | 실린 스킬 목록, 호스트 이벤트 |
| 지시 해석 | 범위·용어·입력 계약을 잘못 읽었다 | 새 실행 trace, 출력 |
| 계획 | 소유자·분기·순서·결정 루프가 틀렸다 | trace, 재시도, 재량으로 채운 곳 |
| 실행 | 도구·명령·검증·변경이 실패했다 | 명령, 파일, Git, 런타임 증거 |
| 형식 | 출력이나 receipt 계약을 어겼다 | 출력 대조 |
| 평가 | grader가 맞는 출력을 틀렸다고 했다 | 산출물과 기준의 대조 |
| 호스트 호환 | Claude Code와 Codex의 호출·로딩·메타데이터 동작 차이 | 호스트별 비교 |
| 로컬 override | 소비 프로젝트의 override나 설정이 원인 | 정확한 override와 그것 없는 대조 |
| 효율 | 결과는 맞는데 피할 수 있는 자원을 썼다 | 같은 조건의 기준선과 비교 |

- 출력은 맞고 채점만 틀리면 본문을 늘리기 전에 평가 평면을 본다.
- 선택은 맞는데 로딩이 다르면 로딩이나 호스트 호환을 본다.
- 같은 결정이 반복되면 실행을 탓하기 전에 가장 이른 약한 단계를 찾는다.
- 자기 보고한 원인 옆에는 결정적 증거가 있어야 한다.

## 정적 정합성

새로 실행하기 전에 frontmatter description과 본문을 대조한다: 긍정·부정 트리거, 능력과 산출물 약속, 승인·변경·실패의 소유자. description에만 있는 약속, 본문에만 있는 동작, 충돌하는 소유자는 가설이다. 정합성만으로 런타임 원인이 증명되지는 않는다.

## 가장 작은 판정 세트

```
사건: 관찰한 프롬프트, 기대 결과, 실제 결과
대조군: 의심 원인을 가르는 가장 가까운 정상 동작
보존: 지켜야 할 핵심 동작, 안전, 라우팅, 권한, 호스트 경계
지표: 실제 기준선 | 표시한 대리 지표 | 없음
```

첫 사건·대조군 쌍이 평면을 못 가를 때만 시나리오를 더한다.

## 새 실행

깨끗한 컨텍스트에서 사건을 한 번 돌린다. 결과가 불안정하거나, 임계값에 가깝거나, 대조군과 애매할 때만 반복한다. 진단이나 후보안을 이미 본 실행자는 새 실행자가 아니다. 실행자에게 기대 답, 판정 기준, 기준선·후보 판정을 보여 주지 않는다.

반복 결과는 재현율로만 쓴다. "N회 연속 통과"는 안정성의 증거가 아니다.

## 최소 실험

사건·대조군 증거로 원인이 직접 증명되지 않을 때만 격리된 사본에서 실험한다. 의심 원인과 그것을 가를 기대 결과를 먼저 적는다. 원인 주제 하나만 바꾸고 영향받는 가장 작은 시나리오만 돌린다. 같은 실패가 반복되는데 문구를 덧쌓지 않는다. 두 번째 실험에는 첫 결과에서 배운 새 원인이 있어야 한다.

## 처분

| 결과 | 처분 |
|---|---|
| 스킬 목표 결함 확인 | 소유 스킬·문서의 범위가 정해진 수정 제안 |
| grader·fixture 결함 | `eval-owner` (evals 수정 제안) |
| 로더·호스트 결함 | `host-owner` |
| 소비자 override가 독립적으로 증명됨 | `local-only` (공용 수정의 대체가 아님) |
| 재현 안 됨 또는 대상이 맞음 | `no change` |
| 결정적 증거 없음 | `unverifiable` + 모든 가설에서 통하는 예방과 판정 검사, 없으면 그 이유 |

효율 절감은 정확성·안전·라우팅 회귀를 상쇄하지 못한다.
