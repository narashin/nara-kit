# readiness: 티켓만으로 구현할 수 있는가

착수 전에 "이 티켓을 워커에게 넘기면 끝까지 갈 수 있는가"를 미리 본다. 기획이 비어 있는 티켓은 워커가 추측으로 메우거나 중간에 멈춘다. 둘 다 착수한 뒤에야 드러나므로 큐에 넣는 시점에 거른다.

## 대상

ready 상태(`ready_statuses`)이면서 타입이 **구현** 또는 **버그픽스**인 티켓만 판정한다.

- 기획: 정의상 내용이 아직 없는 티켓이다. 판정하지 않는다
- 기타: 사람이 직접 처리한다. 판정하지 않는다
- mirror 카드: 이미 손으로 하고 있는 일이다. 판정하지 않는다

## 판정 기준

셋을 모두 만족하면 `ready`, 하나라도 빠지면 `needs-spec`.

| 기준 | 구현 | 버그픽스 |
|---|---|---|
| 무엇을 바꾸는지 특정된다 | 대상 화면·엔드포인트·동작이 본문에서 짚인다 | 관측된 증상과 발생 조건이 적혀 있다 |
| 끝났다는 조건이 있다 | 완료 조건이 적혀 있거나 본문에서 한 가지로만 읽힌다 | 기대 동작이 적혀 있다 |
| 미결 사항이 남아 있지 않다 | 본문에 열린 질문, TBD, 고르지 않은 선택지가 없다 | 같음 |

기준이 **아닌** 것: 구현 방법이 안 적혀 있음(워커가 정한다), 본문이 짧음, 템플릿 머리말이 없음. 한 줄짜리 티켓도 셋을 만족하면 `ready`다.

**애매하면 막지 않는다.** `ready`로 두고 이슈 본문에 `[확인 필요: <무엇>]`을 적는다. 잘못 막은 카드는 멘션까지 받고도 큐에서 빠져 있어 잘못 통과시킨 카드보다 늦게 발견된다. summary만 있고 description이 비어 온 티켓은 추측하지 말고 `needs-spec`으로 둔다.

## needs-spec 처리

카드는 만든다(거울이라 Jira에 있는 티켓은 보드에도 있어야 한다). 만든 직후:

```bash
multica issue status <issue_id> blocked
multica issue metadata set <issue_id> --key triage_block --value "<빠진 것 한 줄>"
multica issue comment add <issue_id> \
  --content "[@<표시명>](mention://member/<MEMBER_ID>) <KEY> 기획 보완 필요: <빠진 것을 질문 형태로, 1~3개>"
```

- `triage_block`은 `drain_state`와 **다른 키**다. `drain_state`는 착수 실행기의 것이고 모르는 값이 들어 있으면 `/drain`을 거부한다
- 빠진 것은 질문으로 적는다. "완료 조건 없음"이 아니라 "저장 실패 시 화면에 무엇이 보여야 하나"
- Jira 티켓에는 코멘트를 달지 않는다. 팀이 보는 곳에 쓰는 건 사람 판단이다

## 풀리는 경로

이 스킬은 `blocked`를 풀지 않는다. 둘 중 하나로 풀린다.

- Jira 본문이나 코멘트가 바뀌면 reconcile이 카드를 `todo`로 되돌린다([Reconcile](reconcile.md)). 다시 판정하지는 않는다. "본문이 바뀌었으니 다시 봐라"는 신호다
- 사람이 카드에 `/drain`을 쓰면 판정과 무관하게 착수한다. 판정은 후보이고 착수 결정은 사람 몫이다
