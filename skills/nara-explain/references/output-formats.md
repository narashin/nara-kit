# Output Format Templates

## Tech Peer (팀원 / 리뷰어)

구현 세부사항과 설계 결정 근거를 포함한다.

```markdown
## [기능/변경 이름]

### 한 줄 요약
[무엇을, 왜]

### 배경
[왜 이 변경이 필요했는지]

### 구현 접근
[어떻게 구현했는지]
- 선택한 방식: [이유]
- 고려했던 대안: [왜 선택 안 했는지]

### 핵심 변경 파일
- `path/to/file.ts` — [역할]
- `path/to/other.ts` — [역할]

### 주의사항 / 사이드이펙트
[있을 경우만]
```

## New Member (신규 입사자 / 온보딩)

전체 맥락과 진입점 중심. 핵심 폴더만, 전체 나열 금지.

```markdown
## [프로젝트/기능 이름] 온보딩 가이드

### 무슨 프로젝트인가요?
[비기술적 한 줄 설명]

### 기술 스택
- [스택 1]: [한 줄 역할]
- [스택 2]: [한 줄 역할]

### 디렉토리 지도
```
[핵심 폴더만]
```

### 진입점
1. `path/to/entry.ts` — 여기서 시작
2. → `path/to/next.ts` — 다음으로 이어짐

### 자주 작업하는 곳
- [작업 유형]: `path/`

### 로컬 실행
```bash
[핵심 커맨드만]
```
```

## Non-tech / PM (기획자 / 비개발자)

코드 스니펫 포함 금지. 사용자 시나리오와 영향 중심.

```markdown
## [기능 이름]

### 무슨 기능인가요?
[비유 또는 사용자 시나리오로 설명]

### 왜 필요한가요?
[문제 → 해결]

### 사용자는 어떻게 달라지나요?
- 이전: [기존 경험]
- 이후: [변경된 경험]

### 알아두면 좋은 것
[제약이나 한계가 있을 경우만]
```

## External / 발표 (컨퍼런스 / 외부 공유)

청중이 공감할 수 있는 문제부터 시작. 기술 용어 최소화.

```markdown
## [제목]

### 문제
[청중이 공감할 수 있는 문제 서술]

### 접근
[왜 이 방식을 선택했는지]

### 결과
[수치, 개선, 임팩트]

### 핵심 교훈
[1~2개]
```

## Change (PR / 커밋 / 브랜치 / 범위 / 작업 트리)

Scope가 변경일 때 audience 템플릿 대신 이것을 쓴다(Non-tech면 코드 인용만 빼고 같은 순서). 순서는 배경부터 흐름까지 읽는 사람이 쌓아 가는 순서다. 핵심 변경 파일 목록이 아니라 실행이 지나가는 길을 따라 설명한다.

**먼저 비교 기준을 고정한다.** 읽는 사람이 나중에 같은 화면을 다시 볼 수 있어야 한다. PR·브랜치는 merge base(`git merge-base <base> <head>`), 커밋 하나는 부모(`<sha>^..<sha>`), 명시 범위는 받은 끝점, 작업 트리는 `HEAD`와 staged·unstaged·untracked 포함 여부. 두 short SHA를 제목에 쓴다.

**보안·스키마·마이그레이션·호환·공개 API 변경은 작아도 "꼭 볼 곳"에 둔다.** "훑어도 되는 곳"에 넣지 않는다.

```markdown
## [변경 이름] (`<base-short>..<head-short>`)

비교 기준: [PR #N은 merge base `<sha>` / 커밋 하나는 부모 `<sha>^` / 범위는 받은 끝점 / 작업 트리는 HEAD `<sha>` + staged·unstaged·untracked 포함 여부]

### 배경
[이 변경 전에 무엇이 안 됐거나 불편했는지. 근거 문서가 있으면 인용]

### 직관
[한두 문장. 무엇을 어디에 끼웠는지를 그림처럼]

### 흐름
1. [진입점] `path/to/file.py:120` [여기서 시작해 무엇을 받는다]
2. [다음 단계] `path/to/file.py:141` [무엇을 바꿔 넘긴다]
3. [끝] `path/to/other.md:12` [결과가 어디에 남는다]
삭제된 동작은 `base:path/to/old.py:88`로 인용한다.

### 꼭 볼 곳 / 훑어도 되는 곳
- 꼭 볼 곳: [보안·스키마·마이그레이션·호환·공개 API 변경, 그리고 동작을 바꾸는 줄] `path:line`
- 훑어도 되는 곳: [문서·이름·테스트 데이터처럼 동작이 안 바뀌는 곳]

### 이해 확인
[읽은 사람이 답해 보면 되는 질문 하나. 답은 `<details>` 안에 둔다]
```

## Brief 형식 (슬랙 / 이메일 / 한 문단)

사용자가 "짧게", "슬랙에 올릴", "한 문단" 요청 시 사용.

```
[한 줄 요약]

- [핵심 포인트 1]
- [핵심 포인트 2]
- [핵심 포인트 3]
[필요 시 한 줄 맥락]
```
