# nara-roadmap: 제약 안에서 추진 방향 잡기

> 출력 형식은 [nara-kit 출력 계약](../nara-now/references/output-contract.md)을 따른다. 이 본문이 다르게 정한 곳은 본문이 우선한다. 파일이 없으면(단독 설치) 이 줄은 건너뛴다.

불분명한 상황을 검토 가능한 로드맵으로 만든다. repo가 없는 비기술 과제도 대상이다. 기획 흐름에서 `nara-ac-draft`·`nara-grill`·`nara-plan`보다 앞에 온다. 결과는 제안이고, 실행 권한을 만들지 않는다.

## 시작

인자 없이 시작할 수 있다. 준비물을 요구하지 않는다. 현재 대화에 맥락이 있으면 그것을 짧게 되짚고 다음 미해결 질문으로 간다. 주제가 없으면 어떤 상황이나 개선을 다루고 싶은지 한 질문만 하고 멈춘다. 이미 답한 인터뷰를 처음부터 다시 하지 않는다.

요청이 이미 정한 기능을 코드 작업 단위·PR 단위로 쪼개는 것이면 로드맵을 만들지 않고 `nara-plan`으로 안내한다.

## 인터뷰 (frontier 라운드)

질문 형식은 `nara-grill`과 같다. 지금 추측 없이 답할 수 있는 사용자 결정 전부를 한 라운드에 묻는다. 질문마다 번호(`Q1`, `Q2`)와 고를 수 있는 안, 근거가 있으면 권고와 짧은 이유를 붙인다. 다른 답에 달린 질문은 미루고 무엇에 걸렸는지 질문 블록 앞에 적는다. 질문 블록이 응답의 마지막 블록이고, 뒤에는 답 형식 안내 한 줄만 둔다. 구분선이나 이모지 장식을 쓰지 않는다. 답을 받으면 반영하고 다음 frontier로 간다. 확인만 하고 끝내지 않는다.

사실은 묻지 않고 대화·제공 자료·읽기 전용 조사로 확인한다. 사용자에게는 선택을 묻는다. "모른다"와 "마감 없음"도 유효한 답이다. 사내 자료를 공개 검색에 넣지 않는다.

**첫 응답의 맥락 반영**: 대화에 이미 나온 마감·역량·담당자·승인 중 출처나 확정자가 없는 것은 `[UNVERIFIED: <무엇이 미확인인지>]`로 표시해 되짚는다. 질문에 앞서 이것을 채워 넣지 않는다.

다루는 순서는 안내이지 설문지가 아니다. 답이 여러 주제에 걸치면 따라간다.

1. **원하는 변화와 필요의 근거**: 무엇이 달라져야 하는지, 누가 혜택을 보는지, 필요하다는 근거가 무엇인지. 이해관계자의 요청인지 스스로 제안하는 탐색인지 구분한다. 수요나 긴급성을 지어내지 않는다.
2. **제약**: 기술·데이터, 역량, 예산, 권한, 의존성, 기존 작업, 마감(있으면), 유지보수. 각각을 `고정` / `협상 가능` / `미확인`으로 가른다.
3. **선택지**: 실질적으로 다른 안을 비교한다. 재사용, 프로세스 변경, 협업, 범위를 정한 조사, 보류를 해당하면 포함한다. 가치·노력·위험·기회비용은 근거가 숫자를 뒷받침할 때만 점수로, 아니면 정성적으로 쓴다.
4. **마일스톤**: 고른 방향을 아래 형식의 마일스톤으로 나눈다.

네 관점을 계속 같이 본다: 혜택받는 사람의 가치, 조직 안에서 추진 가능한지, 실현 가능성, 끝난 뒤 계속 드는 운영 부담. 역할 관점을 빌려도 조직 결정 권한이 생기지 않는다.

## 범위와 마일스톤 규칙

- 범위 상태는 `후보` / `권고` / `합의` 셋을 섞지 않는다. 사용자가 확인한 것만 `합의`다. 확인은 사용자가 가진 중요한 트레이드오프에만 받는다. 단계마다 의례적 승인을 받지 않는다.
- 마일스톤 필드는 `결과` / `범위(포함·제외)` / `완료 증거` / `의존성`이다. `완료 증거`는 관찰 가능한 것으로 쓴다.
- 다음 단계는 자세히, 그 뒤 단계는 거칠고 조건부로 쓴다. 조건부 후속 단계와 제외한 일을 구분한다.
- 반복 운영(정기 점검, 유지보수, 갱신)은 끝이 있는 마일스톤과 따로 `반복 운영`에 적는다.
- 불확실성이 커서 납품 약속이 어려우면 다음 마일스톤을 범위를 정한 조사로 둔다. 조사 마일스톤에는 `질문`, `모을 증거`, `계속 / 보류 / 중단` 판정 기준이 있다.
- 마일스톤 수를 정해 두지 않는다. 근거 있는 중단(no-go), 보류, 조사도 정당한 끝이다. 로드맵은 모든 후보를 해내겠다는 약속이 아니다.
- 날짜, 담당자, 목표 수치, 역량, 승인을 지어내지 않는다. 비면 `[UNVERIFIED: ...]`로 두거나 `열린 가정과 결정`에 남긴다.

## 출력

방향을 고를 만큼 정보가 모이면 짧은 제안을 낸다. 방향이 합의되거나 사용자가 초안을 요청하면 로드맵을 낸다. 섹션은 다음 여섯 개이고 이름을 바꾸지 않는다.

`목표와 결정 제약` / `권고 방향` (보류·제외한 대안과 이유 포함) / `마일스톤` / `반복 운영` / `열린 가정과 결정` / `다음 행동` (하나)

기본은 대화다. 대화에서는 섹션 이름을 굵은 줄로 쓰고 헤더를 쓰지 않는다. 사용자가 저장을 명시하면 같은 내용을 `docs/plan/roadmap-<slug>.md` 한 파일에 `##` 섹션으로 쓴다. 골격과 예시는 [roadmap-format](references/roadmap-format.md).

부수효과가 없다. 티켓 생성, 구현, 담당 배정, 원격 게시, 다른 스킬 자동 호출을 하지 않는다. 다음 경로는 쓸모 있을 때만 하나 이름 붙인다: 외부 접근법 비교 `nara-research`, 계획 찔러보기 `nara-grill`, 요구사항 `nara-ac-draft` / `nara-prep`, 고른 단계의 코드 작업 분할 `nara-plan`.

## Receipt (로드맵을 냈을 때)

```
로드맵 초안 완료 (recorded only).
- 방향: <권고 한 줄> · 범위: 후보 n / 권고 n / 합의 n
- 마일스톤 n · 반복 운영 n · UNVERIFIED n
- artifact: `docs/plan/roadmap-<slug>.md` | chat-only
- next: <다음 행동 하나>
```

인터뷰 라운드 응답에는 receipt를 붙이지 않는다. 질문 블록이 마지막이다.

## Error Handling (if-then)

| 트리거 | 대응 |
|---|---|
| 주제도 맥락도 없음 | 다룰 상황을 한 질문으로 묻고 멈춘다 |
| 코드 작업·PR 단위 분할 요청 | 로드맵을 만들지 않고 `nara-plan`으로 안내 |
| 사용자가 날짜·담당자·수치를 채워 달라 함 | 근거가 없으면 채우지 않고 `[UNVERIFIED: ...]`로 둔다 |
| 근거가 방향을 못 가름 | 다음 마일스톤을 조사 마일스톤으로 둔다 |
| 추진할 이유가 약함 | no-go 또는 보류를 이유와 함께 결론으로 낸다 |
| `docs/plan/roadmap-<slug>.md`가 이미 있음 | 덮어쓰기 전 확인. 확인 없으면 쓰지 않는다 |
| 파일을 쓸 수 없음 | 같은 내용을 대화로 내고 receipt에 `chat-only (<사유>)` |
