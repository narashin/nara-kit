# 카드 코멘트 제스처 — /ask, /post, /approve

리뷰 파이프라인은 PR에 대해 read-only다. 판정은 카드 코멘트로만 남고, 판정을 쓴 세션은 수집 시점에 워크트리와 함께 사라진다. 그래서 사람이 손대지 않으면 판정은 PR에 영원히 안 올라가고, 되물을 곳도 없다. 이 문서는 그 이후 한 걸음의 계약이다.

## 제스처

**카드에 코멘트를 쓴다.** 이게 기본 경로다.

| 코멘트 | 결과 |
|---|---|
| `/ask <질문>` | 판정에 대해 되묻는다. 답이 **그 질문 아래 스레드로** 돌아온다 |
| `/ask --sol <질문>` | 같은 되묻기를 무거운 모델로 |
| `/post` | 판정을 PR 리뷰 코멘트로 게시 (`gh pr review --comment`) |
| `/approve` | approve + 코멘트 게시 (`gh pr review --approve`) |

토큰은 **코멘트 맨 앞**에 있어야 한다. 뒤에 하고 싶은 말을 이어 써도 된다(`/post 이대로 올려줘`). "나중에 /post 할게" 같은 문장은 발동하지 않고, `/poster`도 `/asked`도 아니다. 스크립트가 쓰는 코멘트는 전부 멘션으로 시작하므로 자기 코멘트에 스스로 걸리지 않는다.

`/post` `/approve`는 라벨 `post-comment` / `post-approve`로도 같은 동작을 한다. 다만 GUI에 라벨 UI가 없어서 CLI 전용 경로이고, `issue label add`가 이름이 아니라 label UUID를 받는다. **코멘트가 사람이 실제로 쓸 수 있는 경로다.** `/ask`에는 라벨 짝이 없다. 질문은 본문이 필요해서 라벨로 표현할 수 없다.

**status 드래그가 아닌 이유.** 남의 PR에 게시하는 것은 바깥으로 나가는 행동이고, 컬럼 이동이 암시할 성격이 아니다. 그리고 approve는 머지 신호다. `status: pass` 판정에서 자동 유도하면 안 되고, 사람이 approve를 명시한 것만이 근거다.

게시 라벨이 둘 다 붙어 있으면 아무것도 게시하지 않고 카드에 알린다. 추측하지 않는다.

**모든 거부는 카드에 이유를 남기고 트리거를 소비한다.** 판정 없는 카드, PR 주소 없음, repo 매핑 없음, 질문 없는 `/ask` 모두 그렇다. 소비하지 않으면 같은 요청을 매 폴링마다 다시 읽어 같은 불만을 분당 하나씩 쌓는다. 조용히 무시하는 것은 이 파이프라인이 반복해서 만들어낸 실패 모양이라 하지 않는다.

같은 카드에 다시 `/post`나 `/ask`를 쓰면 다시 실행된다. 소비 기준은 **코멘트 id**(`post_trigger_id` / `ask_trigger_id`)라서 새 코멘트는 새 요청이다. `/ask`에서는 이 반복이 곧 대화다.

## /ask — 판정에 되묻기

판정만 있고 물을 곳이 없던 것이 이 제스처의 이유다. 리뷰는 헤드리스 워크트리에서 돌고 수집과 함께 그 워크트리가 제거되므로, 사람이 판정을 읽는 시점에 판정을 쓴 세션은 존재하지 않는다. 재리뷰는 대안이 아니다. 새 리뷰는 카드를 읽지 않아서 질문을 볼 수 없고, 같은 판정을 다시 낸다.

`/ask`는 같은 PR에 새 세션을 띄우고, 그 세션에 리뷰가 볼 수 없었던 두 가지를 준다: **먼저 나온 판정문**과 **질문**. 한 번의 `/ask`는 한 왕복이고, 더 물으면 `/ask`를 다시 쓴다.

프롬프트가 세션에 강제하는 것:

- 판정문을 **남의 주장으로** 취급한다. 오탐이면 오탐이라고 답하는 것이 이 실행의 목적이고, 판정을 방어하는 것은 실패다
- 질문에만 답한다. 답하는 과정에서 발견한 새 문제는 추가 발견임을 밝혀 끝에 덧붙인다
- 근거는 파일:줄. 확인 못 한 것은 "확인 못 했다"고 쓴다
- PR에 아무것도 게시하지 않고, 코드도 건드리지 않는다

**판정문 없이도 답한다.** 아직 리뷰가 안 돌아간 카드에서 질문을 거부하는 것은 "물어본다"는 말의 이상한 해석이다. 이 경우 프롬프트가 판정문 부재를 명시하고 PR만 근거로 답하게 한다.

답은 `--parent`로 질문 아래에 달린다. 질문과 답은 한 번의 주고받음이고, 평평한 카드에서는 여러 왕복이 파이프라인 자신의 상태 코멘트와 뒤섞인다.

### 모델은 왜 여기서만 고르는가

모든 실행은 기본적으로 로컬 config의 모델을 상속하고, **자동 peer review도 그렇다.** 비용 결정이다. peer review는 리뷰 요청이 들어오는 PR마다 발동해서 그게 물량이고, `/ask`는 사람이 쳐야 돈다. 대량 경로를 비싸게 만들면 아무도 다투지 않는 PR까지 값을 치른다.

그래서 escalation 레버를 다툼이 있는 자리에 뒀다. 판정이 얇거나 납득이 안 되는 건에만 `--sol`로 다시 묻는다. 자동 패스에는 플래그를 실을 제스처가 없어서 override가 아예 없다 — 그 판정을 무거운 모델로 다시 보는 방법이 `/ask --sol`이다.

플래그는 **선행 위치에서만** 읽는다. `/ask 왜 --sol 이게`는 `--sol`을 질문 본문으로 남긴다. 문장 중간에서 플래그가 주워지지 않는 예측 가능한 규칙이 낫다.

`--model <이름>` 자유 지정이 아니라 알리아스 하나인 이유: 모델명은 오타 나면 게이트웨이가 거부하는 문자열이고, 그걸 알아챌 사람이 이 경로에 없다. 그래서 **선행 `--`로 시작하는 다른 토큰은 오타로 보고 거부한다.** `--sonnet`으로 시작하는 질문에 조용히 답하면 모델이 안 바뀐 사실이 묻힌다.

답변 코멘트는 어느 모델이 답했는지 제목에 적는다. 기본 모델의 얇은 답은 `--sol`로 다시 물을 이유이고 `--sol`의 얇은 답은 그렇지 않은데, 라벨이 없으면 그 둘이 같아 보인다.

config의 `model_context_window` 계열은 기본 모델 기준으로 잡혀 있고 `--sol` 모델에 맞는 값인지는 확인되지 않았다. 게이트웨이 `/v1/models`가 context length를 노출하지 않는다.

## 왜 스크립트가 아니라 에이전트인가

판정문은 **보드용으로 쓰인 글**이다. `status:` / `blocking:` 같은 기계용 헤더, "PR에는 게시하지 않았다", "사람이 정한다" 같은 내부 문구, 워크트리·카드 언급이 섞여 있고 언어도 보드 기준이다. 그대로 내보내면 안 된다.

그래서 게시는 워크트리 세션에서 돈다. 하는 일은 다시 쓰기 하나다:

1. 내부 문구·기계 헤더 제거
2. 대상 repo의 언어 관행에 맞추기 (`nara-pr-review`의 게시 규칙과 동일)
3. 지적 내용·근거·심각도는 **변경 금지**. 없던 지적 추가 금지, 있는 지적 누락 금지
4. 코드 위치는 파일:줄로 유지

판정 자체를 다시 하지 않는다. approve 여부도 다시 판단하지 않는다 — 판정문이 수정을 요구하는데 `post-approve`가 붙어 있으면 게시를 거부하고 이유를 보고한다.

`/ask`도 같은 이유로 세션이다. 다만 방향이 반대다. 게시는 판정을 고정한 채 문체만 바꾸고, `/ask`는 문체를 놔둔 채 판정을 다시 확인한다.

## 금지

- 코드 수정·커밋·push·머지. 게시 실행은 게시 하나만, 답변 실행은 답변 하나만 한다
- 인라인 코멘트를 개별로 흩뿌리기. 리뷰 하나로 게시한다
- 중복 게시. 성공 후 라벨이 제거되고 `post_state=posted`가 남는다
- `/ask` 실행이 PR에 무엇이든 남기기. 산출물은 카드 코멘트 하나다

## metadata 계약

게시:

| 시점 | 상태 |
|---|---|
| 착수 | `post_state=dispatched` · `post_action=comment\|approve` · `post_trigger_id`(소비한 코멘트 id) · `post_worktree` · `post_worktree_sel` · `post_prompt_state=pending` |
| 성공 | 라벨 제거 → `post_state=posted` → 워크트리 제거 → 게시 본문을 카드 코멘트로 |
| 실패·거부 | 라벨 제거 → `post_state=failed\|refused` → **워크트리 유지**(원인 확인용). 다시 붙이려면 `post_state` 삭제 |

답변:

| 시점 | 상태 |
|---|---|
| 착수 | `ask_state=dispatched` · `ask_trigger_id`(소비한 질문 코멘트 id) · `ask_model` · `ask_worktree` · `ask_worktree_sel` · `ask_prompt_state=pending` |
| 성공 | `ask_state=answered` → 워크트리 제거 → 답변을 질문 아래 스레드로 |
| 실패 | `ask_state=blocked\|failed` → **워크트리 유지**. 다시 물으려면 새 `/ask` 코멘트 (state를 지울 필요 없다) |

`post_*` · `ask_*` · `review_*`는 서로 별개 키다. 판정·게시·답변은 다른 실행이고 재시도 조건도 다르다. 별개라서 한 카드에서 질문과 게시가 동시에 떠 있어도 서로의 상태를 덮지 않는다.

카드가 `cancelled`로 가면 살아 있던 리뷰어와 답변 세션을 **둘 다** 정리한다. `ask_review`도 `cancelled`를 훑지 않으므로, `review_state`만 보고 판단하면 진행 중인 질문이 워크트리째 남는다.

## status는 건드리지 않는다

게시가 성공하면 GitHub의 `reviews[].author.login`에 내가 들어간다. 그 시점부터 `nara-review-reminder`의 reconcile이 카드를 `done`으로 닫는다. 여기서 별도로 닫으면 reconcile 계약에 없는 종료 조건을 또 만드는 것이고, 그게 바로 판정을 `done`으로 찍어서 갚아야 할 리뷰를 보드에서 지웠던 결함이다.

`/ask`도 같다. 질문에 답한 것은 리뷰를 갚은 것이 아니므로 카드는 그대로 둔다.
