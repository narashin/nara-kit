# UI 증거 수집: 라벨과 진입 경로

이 문서는 새 권한을 주지 않는다. 부르는 스킬이 이미 가진 조사 범위 안에서만 읽는다. 읽기 전용이고, 화면을 바꾸는 조작은 하지 않는다.

PR 본문, QA 시트, 테스트 시나리오에 적힌 버튼 이름이 실제 화면과 다르면 읽는 사람은 그 버튼을 찾다가 문서 전체를 의심하게 된다. 그럴듯한 이름 하나가 틀린 것이, 이름을 비워 둔 것보다 비싸다.

## 무엇이 증거인가

| 주장 | 증거가 되는 것 | 증거가 아닌 것 |
|---|---|---|
| 이 라벨이 화면에 있다 | 대상·환경·로케일·역할이 맞는 런타임 렌더, 렌더 경로에 연결된 소스, 출처가 있는 캡처 | 라우트, 컴포넌트명, 식별자, enum, i18n 키, 용어집, 티켓 문구 |
| 이 경로로 들어간다 | 메뉴 단계마다 실제로 밟고 확인한 라벨과 연결 | 도착 화면의 제목, breadcrumb, URL |
| API가 주는 문구다 | 실제 응답과 그것이 렌더되는 변환 지점 | 스키마 (모양만 증명한다) |

breadcrumb과 페이지 제목은 거기 표시된 문자열과 계층만 증명한다. 사이드바 라벨이 breadcrumb과 같다는 것도, 그 메뉴를 눌러 들어왔다는 것도 증명하지 않는다. breadcrumb만 봤으면 "표시된 계층"으로 적고 클릭 안내문으로 쓰지 않는다.

## 수집 순서

1. 진입해서 초기 렌더가 끝난 뒤 `document.body.innerText`를 **한 번** 받는다. 라벨을 추측해 셀렉터로 하나씩 찔러보기 전에 한다.
2. 그 결과는 지금 렌더된 문자열의 목록일 뿐 메뉴 트리 전체가 아니다. 접힌 내비게이션은 안전한 것만 펼치고, 빠진 영역만 추가로 본다.
3. 화면 전체 덤프에 비밀값이나 무관한 개인정보가 섞이면 내비게이션·헤더 영역만 보고, 그렇게 좁혔다는 사실을 남긴다.
4. 라벨마다 대상·환경·로케일·역할과 수집 출처를 함께 기록한다. 로케일이나 역할이 다르면 다른 주장이다.

## 쓰는 규칙

- 기존 라벨은 언어·대소문자·문장부호·띄어쓰기까지 그대로 인용한다.
- 제안하는 새 문구는 기존 라벨과 섞지 않고 따로 표시한다.
- 출처끼리 충돌하면 하나를 고르지 않고 충돌을 그대로 보고한다.
- 사용자가 글로 알려준 라벨은 `user-provided`다. 그 주장 하나만 해소하고, 독립적으로 관찰한 것처럼 쓰지 않는다.
- 그럴듯한 경로를 "추정"이라는 단서를 달아 안내문으로 쓰지 않는다. 단서를 달아도 읽는 사람은 따라간다.

## 못 구했을 때

저장소에서 못 찾았다고 멈추지 않는다. 범위 안에서 읽기 전용 브라우저 조사가 가능하면 먼저 시도한다. 그래도 없으면 해당 주장을 `Unverifiable`로 두고 다음 넷을 적는다.

- 어떤 라벨 또는 어떤 연결이 비었는가
- 지금 가진 증거와 그 출처
- 왜 못 구했는가 (다른 저장소가 메뉴를 소유, 권한 없음, 환경 미기동 등)
- 채우는 데 필요한 **가장 작은 입력**: 내비게이션이 보이는 스크린샷 한 장, 라벨·계층·라우트만 남긴 메뉴 API 응답, 소유 소스 경로

자격 증명이나 가리지 않은 응답 전체를 채팅으로 요청하지 않는다. 확인된 부분 결과와 대기 중인 요청은 완료 보고, PR의 한계 절, 핸드오프에 그대로 싣는다. 빈 칸을 조용히 빼거나 확인된 것으로 세지 않는다.
