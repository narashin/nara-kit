# 파생 문서: 화면 설계서와 운영 개발 요청서

파생 문서는 묶음에 이미 있는 기준 정보(PRD, 정책, 흐름, IA, 근거, 요구사항)를 읽는 사람에게 맞게 다시 묶은 것이다. 새 사실을 만들지 않는다. 문서에 쓰는 모든 내용은 원래 있는 곳이 있고, 그곳이 바뀌면 파생 문서를 다시 만든다. 그래서 같은 내용이 두 곳에서 따로 고쳐지는 일이 없다.

## 공통 규칙

- **조립하기 전에 원본끼리 대조한다.** 파생 문서는 여러 원본을 한 장에 모으기 때문에, 원본끼리 다르게 적힌 사실이 가장 잘 드러나는 곳이자 가장 쉽게 묻히는 곳이다. SKILL.md 절차의 정합성 점검을 먼저 하고, 어긋난 사실은 어느 한쪽 값으로 쓰지 않는다. 그 자리에 "정해지지 않음: <문서 A>는 <값>, <문서 B>는 <값>"으로 쓰고 receipt에서 가장 먼저 알린다.
- **재료가 없으면 그 절을 지어내지 않는다.** 만들기 전에 필요한 재료를 확인한다. 빠진 재료가 있으면 그 절을 비우지 말고 "이 절에 필요한 것: <무엇>" 한 줄을 남기고, receipt에서 무엇을 먼저 채워야 하는지 알린다. 재료가 절반도 없으면 문서를 만들지 않고 먼저 채울 것을 안내한다.
- **원본을 가리킨다.** 내용을 옮길 때는 짧게 요약하고 뜻이 적힌 링크로 원본을 가리킨다: `[고액 환불은 정산 담당자만 승인](policy.md#고액-환불은-정산-담당자만-승인)`. 원본 문단을 통째로 복사하지 않는다.
- **직접 고친 흔적을 지키는 법.** frontmatter에 `derived: true`, 만든 날짜, 읽은 원본 파일, 그리고 본문 해시(`content_sha`)를 남긴다. 다시 만들 때 현재 본문 해시가 기록과 다르면 누군가 손으로 고친 것이다. 덮어쓰지 않고 무엇이 바뀌었는지 보여 준 뒤, 그 내용을 원본(정책, 흐름 등)으로 옮길지 묻는다.
- **이슈 절만은 이 문서가 주인이다.** 화면 설계서의 "이슈" 절은 검토 중에 나온 화면 단위 문제를 쌓는 곳이라 다시 만들 때도 그대로 둔다. `<!-- issues:start -->`와 `<!-- issues:end -->` 사이를 보존한다. 이슈가 기획 결정으로 이어지면 PRD 결정 로그나 열린 질문으로 옮기고 이슈에는 "옮김: <어디로>"를 적는다.
- **번호 참조를 쓰지 않는다.** 화면, 규칙, 이슈를 번호로만 부르지 않는다. 이름과 뜻으로 쓰고, 추적 키는 HTML 주석으로 숨긴다.

## 화면 설계서 (`screens.md`)

화면을 만드는 디자이너와 개발자, 그리고 검토하는 사람이 읽는다. 외부 사용자 화면(프론트)과 내부 사용자 화면(어드민)을 나눠 쓴다. 화면이 많으면 `screens-front.md`, `screens-admin.md`로 나눠도 된다.

필요한 재료: IA(어떤 화면이 있나), 흐름(화면 사이 이동), 정책(권한과 상태), 요구사항의 인수 기준. 목표와 KPI는 PRD에서, 수정 대상은 근거 원장의 코드 항목에서 온다.

```markdown
---
derived: true
generated: <YYYY-MM-DD>
sources: [prd.md, policy.md, flows.md, ia.md, ../../requirements.md]
content_sha: <본문 sha256 앞 12자>
---

# <기능 이름> 화면 설계서

## 개요
<이 기능이 무엇을 바꾸는지 두세 문장. PRD 문제와 범위 요약 + 링크>

## 목표와 기대효과
<PRD의 목표와 KPI를 한 줄씩. 계산식과 목표값은 PRD 링크로. 가정이면 [가정] 그대로>

## 화면 목록
<IA에서 이번에 새로 생기거나 바뀌는 화면만. 프론트/어드민 구분, 진입 경로>

<흐름 문서의 해당 흐름을 화면 이름으로 다시 적은 단계 목록. 분기와 실패 경로 포함>
```

화면별 동작 표의 "결과"와 "막히는 경우"는 정책과 인수 기준에 있는 것만 쓴다. 정책에 없는 오류 문구나 버튼 이름을 지어내지 않는다. 화면 문구가 미정이면 "문구 미정"이라고 쓴다. 시각 시안이 필요하면 다음 단계로 `/nara-design-studio`를 묻는다.

## 운영 개발 요청서 (`ops-request.md`)

이미 운영 중인 서비스에 작은 변경을 개발팀에 요청할 때 쓴다. 읽는 사람은 요청을 받아 일정과 방법을 정할 개발자다. 기획 묶음 전체를 읽지 않아도 판단할 수 있게 한 장으로 쓴다.

필요한 재료: 문제와 근거, 코드로 확인한 현재 동작, 바라는 동작(결정 로그), 인수 기준. 정책이 바뀌면 정책 문서.

```markdown
---
derived: true
generated: <YYYY-MM-DD>
sources: [prd.md, evidence.md, policy.md, ../../requirements.md]
content_sha: <본문 sha256 앞 12자>
---

# <요청 제목: 무엇을 어떻게 바꿔 달라는지 한 줄>

## 왜 필요한가
<문제와 근거를 두세 문장. 근거가 가정이면 가정이라고 쓴다>

## 지금 동작
<코드로 확인한 현재 동작. 경로:라인 포함>

## 바라는 동작
<결정 로그의 결정을 문장으로. 결정 안 된 것은 "정해지지 않음"과 누가 정하는지>

## 바뀌는 정책
<바뀌거나 새로 생기는 규칙. 없으면 "없음">

## 영향 범위
- 화면: <바뀌는 화면. 없으면 없음>
- 데이터: <저장 구조, 기존 데이터 처리. 모르면 "개발 확인 필요">
- 운영: <CS, 정산 등 사람 작업의 변화>

## 완료 기준
<인수 기준을 문장으로. 기획자가 직접 확인할 방법 한 줄>

## 아직 정하지 않은 것
<열린 질문 중 이 요청에 걸린 것>

## 일정과 우선순위
<사용자가 말한 것만. 말하지 않았으면 이 절을 쓰지 않는다>
```

"영향 범위"는 근거 원장의 코드 항목과 정책에서 읽을 수 있는 것만 쓴다. 저장 구조나 마이그레이션처럼 기획자가 확인할 수 없는 것은 추정하지 않고 "개발 확인 필요"로 둔다.
