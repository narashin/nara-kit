# 기획 묶음 형식

## 구조

```
docs/product/<slug>/
  prd.md            # 필수. 상태, 커버리지 표, 문제·대상·가치 제안·목표·범위·결정 로그
  evidence.md       # 근거가 하나라도 있으면. 형식은 evidence.md reference
  policy.md         # 조건부
  flows.md          # 조건부
  ia.md             # 조건부
  requirements.md   # 개발 중이 아닐 때만 여기 있다 (아래 "요구사항 이동")
  screens.md        # 파생, 요청 시. 화면 설계서 (derived-docs reference)
  ops-request.md    # 파생, 요청 시. 운영 개발 요청서
```

`<slug>`는 기능을 줄인 영문 소문자와 하이픈이다. 브랜치 이름에 같은 slug가 들어가면 인자 없이 이어 갈 수 있다. 저장소에 이미 기획 문서 위치나 같은 내용을 다루는 문서가 있으면 그 위치와 이름을 따르고, 대소문자만 다른 새 파일을 만들지 않는다.

## prd.md 골격

```markdown
---
status: drafting
slug: <slug>
created: <YYYY-MM-DD>
requirements: docs/requirements.md | docs/product/<slug>/requirements.md | none
---

# <기능 이름>

## 커버리지

| 항목 | 구분 | 상태 | 근거·출처 | 채우는 데 필요한 것 |
|---|---|---|---|---|
| 문제와 근거 | 필수 | 미결 | | 사용자 인터뷰 또는 문의 데이터 |
| ... | | | | |

## 문제
## 대상 사용자
## 가치 제안
## 목표와 KPI
## 범위
## 결정 로그
## 열린 질문
## 관련 문서
```

내용이 없는 절은 쓰지 않는다. 그 사실은 커버리지 표에 남는다. 본문 문장에 근거가 있으면 근거를 뜻으로 풀어 단다(아래 "참조 쓰는 법"). 가정은 `[가정]`으로 시작한다.

## 문서 쓰는 법

기획 문서는 처음 보는 사람이 훑어서 읽는다.

- 표의 칸에는 짧은 말만 쓴다. 상태 칸은 `확정`, `가정`, `미결`, `해당 없음` 중 하나만. 설명이 한 줄을 넘으면 칸에는 요지만 쓰고 자세한 내용은 아래 절이나 열린 질문으로 옮긴다.
- 한 줄에 사실 하나. `·`로 사실 여러 개를 이어 붙이지 않는다. 필드가 여럿이면 줄을 나눈다.
- 링크 글자는 짧은 뜻으로 쓴다. 문장 전체를 링크로 만들지 않는다.

## 참조 쓰는 법

기획 문서는 배경을 모르는 사람이 읽는다. `(E-3 참고)`, `P-1`, `D-2`, `PROJ-123 참고`처럼 번호만 적힌 참조는 독자가 다른 곳을 찾아가야 뜻을 알 수 있어서 쓰지 않는다. 대신 이렇게 쓴다.

- **뜻을 쓴다.** `(근거: 10월 14일 고객 인터뷰, 환불 상태를 몰라 두 번 문의함)`처럼 무엇이 근거인지 문장으로 적는다.
- **따라가야 하면 링크로 쓴다.** 링크 글자는 뜻이고 주소가 위치다: `[환불 상태를 몰라 두 번 문의한 인터뷰](evidence.md#환불-상태를-몰라-두-번-문의한-고객)`. 티켓도 `[환불 승인 화면 개선 티켓](<URL>)`처럼 쓴다.
- **추적용 키는 숨긴다.** 영향 확인을 하려면 기계가 찾을 키가 필요하다. 항목마다 제목 바로 아래 `<!-- id: decision-high-value-approver -->`처럼 뜻이 드러나는 영문 키를 HTML 주석으로 두고, 그 항목을 참조하는 문장 끝에도 `<!-- ref: decision-high-value-approver -->`를 단다. 주석은 화면에 보이지 않는다. 키에 순번을 쓰지 않는다.
- 인터뷰 참가자처럼 실명을 숨겨야 하는 대상은 `참가자 A (단골 고객, 지난달 환불 2회)`처럼 처음 나올 때 특징을 같이 쓰고, 그 뒤로는 `참가자 A`라고만 써도 된다.
- 대화 응답(receipt)에서도 같은 원칙이다. `근거 2 (E-3, E-4)`가 아니라 `근거 2건 (고객 인터뷰 2)`라고 쓴다.

## 커버리지 표

필수 정보는 문서가 아니라 정보다. 모든 기능에 있어야 한다.

| 항목 | 채워진 것으로 보는 조건 |
|---|---|
| 문제와 근거 | 문제 한두 문장과 그 근거(뜻으로). 근거가 없으면 "근거 없음, 가정"이라고 명시한 것도 채워진 것이다 |
| 대상 사용자 | 내부·외부 구분. 역할 이름 |
| 가치 제안 | 대상마다 6요소: 누구, 왜(해야 할 일과 막는 문제), 지금은(현재 방식과 불편), 어떻게, 달라진 뒤, 대안(우리 없이 쓸 것과 우리를 고를 이유) |
| 목표와 KPI | KPI 정의표 한 줄 이상(evidence reference의 형식). 측정할 수 없으면 그 사실과 이유 |
| 범위 | 첫 릴리스에 넣을 것, 나중에 할 것, 하지 않을 것 |
| 인수 기준 연결 | `requirements:` 경로와 AC 수. `nara-ac-draft`가 채운다 |

상태 값은 `확정`(출처 있음), `가정`(`[가정]` 라벨 붙여 본문에 씀. 사용자가 채우라고 한 값도 여기), `미결`(본문에 쓰지 않음), `해당 없음`(사유 한 줄)이다. 측정해야 아는 값(기준선 등)은 가정으로 채우지 않고 `미결`로 둔다. "완료"는 모든 질문에 답한 것이 아니라 첫 릴리스 결정을 막는 미결이 없는 것이다.

## 조건부 문서

조건이 맞을 때만 만든다. 맞지 않으면 표에 `해당 없음`과 사유를 적는다.

| 문서 | 만드는 조건 | 담는 것 |
|---|---|---|
| `policy.md` | 역할이 둘 이상, 상태가 바뀌는 대상, 돈·개인정보·승인 중 하나 | 권한 매트릭스, 상태 전이표, 예외 처리, 운영 규칙 |
| `flows.md` | 행위자가 둘 이상이거나 단계가 화면·시스템을 넘나듦 | 흐름마다 행위자, 시작 조건, 단계, 끝 상태 |
| `ia.md` | 새 화면·메뉴가 생기거나 내비게이션이 바뀜 | 화면 목록과 계층, 진입 경로, 화면별 주요 요소 |

권한 매트릭스는 `역할 × 대상 × 행위 → 허용/거부`이고 거부일 때 사용자에게 무엇이 보이는지를 같이 적는다. 상태 전이표는 `현재 상태 | 사건 | 누가 | 조건 | 다음 상태 | 실패하면` 열이다. 규칙은 번호 대신 한 줄 이름(예: "고액 환불은 정산 담당자만 승인")을 제목으로 쓰고 숨긴 추적 키를 단다. 흐름에서 권한이 걸리는 단계에는 그 규칙 이름을 그대로 적는다.

화면 설계서와 운영 개발 요청서는 요청할 때 위 문서를 참조로만 조립한다([derived-docs](derived-docs.md)). 운영 가이드와 테스트 연결 표는 아직 만들지 않는다.

## 상태

| 상태 | 들어가는 조건 | nara-now |
|---|---|---|
| `drafting` | 묶음 생성, 또는 사용자가 명시적으로 다시 열 때 | `/nara-planning` 추천 |
| `handed-off` | 필수 칸에 `미결`이 없고, 남은 `가정`마다 "가정인 채로 진행" 결정이 결정 로그에 있고, 묶음에 `<!-- src: -->` 마커가 있으면 `nara-claim-audit` 결과에 `mapping_failure`·`syntax_error`가 없고, `nara-ac-draft`가 이 묶음을 참조한 요구사항을 썼다 | 기존 개발 판단으로 |
| `measuring` | 출시 후, KPI 정의표의 측정 시점이 지났다 | 주 추천은 그대로, 측정 기록 안내 한 줄 |
| `closed` | 측정 결과를 근거 원장에 기록했고 사용자가 닫자고 했다 | 추천 안 함 |

`handed-off`에서 `drafting`으로 되돌리는 것은 사용자의 명시적 요청으로만 한다. 이때 바뀔 결정에 걸린 인수 기준을 문장으로 먼저 보여 준다. 상태를 바꿀 때마다 결정 로그에 한 줄 남긴다.

## 결정 로그

```markdown
### 고액 환불은 정산 담당자만 승인한다
<!-- id: decision-high-value-approver -->
- 날짜: 2026-10-16
- 출처: 결정 질문 라운드에서 사용자 확인 ("정산팀만")
- 관련: [고액 환불 승인 권한](policy.md#고액-환불-승인-권한)

### 부분 환불은 첫 릴리스에서 하지 않는다
<!-- id: decision-no-partial-refund-v1 -->
- 날짜: 2026-10-15
- 출처: 사용자 답
- 대체됨: 2026-10-20, "부분 환불은 고객센터 수동 처리로 첫 릴리스에 포함"으로 바뀜
```

출처가 없는 결정은 로그에 쓰지 않고 열린 질문으로 둔다. 결정은 지우지 않는다. 바뀌면 `대체됨:`에 날짜와 새 결정의 내용을 적고, 새 결정은 새 제목으로 쓴다.

## 갱신과 영향 확인

기존 파일은 덮어쓰지 않고 바뀐 절만 고친다. 고치기 전에 바뀌는 사실의 숨긴 추적 키(`ref: <키>`)와 그 사실의 핵심 문구를 `docs/requirements.md`, `docs/product/` 아래 모든 묶음, `docs/test-scenarios/`에서 찾는다. 찾은 곳을 "영향받는 곳" 목록으로 보여 주되, 파일과 그 문장을 뜻으로 보여 준다. 확인을 받은 뒤 고친다. 다른 파일을 이 스킬이 대신 고치지 않는다. AC를 고쳐야 하면 `nara-ac-draft`로 이어 간다.

## 요구사항 이동

기능 하나의 AC는 한 곳에만 있다. 개발 중인 기능은 `docs/requirements.md`, 나머지는 각 묶음의 `requirements.md`다.

1. 새 기능을 개발로 넘기려는데 `docs/requirements.md`가 이미 있으면 frontmatter의 `product:` 값으로 주인 묶음을 확인한다.
2. `product:`가 없거나, 그 경로가 없거나, `git status`에 그 파일의 미커밋 변경이 있으면 멈추고 알린다.
3. 주인 묶음으로 파일을 옮기고(`git mv` 또는 이동), 그 묶음 `prd.md`의 `requirements:` 값을 바꾼다.
4. 새 기능 묶음에 `requirements.md`가 있으면 `docs/requirements.md`로 옮기고 값을 바꾼다. 없으면 `nara-ac-draft`로 이어 간다.

옮기기 전에 무엇을 어디로 옮기는지 보여 주고 확인을 받는다. 두 기능을 동시에 개발하려면 worktree를 나눈다.
