# nara-planning: 기능 기획 묶음과 다음 단계

> 출력 형식은 [nara-kit 출력 계약](../nara-now/references/output-contract.md)을 따른다. 이 본문이 다르게 정한 곳은 본문이 우선한다. 파일이 없으면(단독 설치) 이 줄은 건너뛴다.

기능 하나의 기획 묶음 `docs/product/<slug>/`를 이 스킬만 쓴다. 묶음에는 PRD(`prd.md`), 근거 원장(`evidence.md`), 해당할 때만 정책(`policy.md`)·흐름(`flows.md`)·IA(`ia.md`), 그리고 요청할 때 만드는 파생 문서(화면 설계서 `screens.md`, 운영 개발 요청서 `ops-request.md`)가 있다. 다른 스킬은 묶음을 읽기만 한다. 상세 요구사항과 AC는 `nara-ac-draft`가 `docs/requirements.md`에 쓴다.

진행은 `prd.md` 머리의 **커버리지 표**가 정한다. 사용자가 명령 순서를 외울 필요가 없게, 부를 때마다 표를 읽고 다음 할 일 하나를 고른다. 이 스킬은 흐름을 이끌지만 다른 스킬을 대신하지 않는다. 남의 몫은 묻고, 동의를 받아 같은 세션에서 그 스킬을 실행한 뒤 결과를 묶음에 기록한다.

## Core Rules

1. **본문에는 확정과 표시된 가정만 쓴다.** 확정은 출처가 있는 것이다: 사용자 답(인용과 날짜), 근거 원장 항목, `nara-grill` Receipt의 `confirmed` 결정. 근거 없는 수치·정책·우선순위·일정·담당자는 본문에 쓰지 않고 커버리지 표의 `미결`로 둔다. 사용자가 "그냥 채워"라고 하면 `[가정]` 라벨을 붙여 쓰고 표 상태도 `가정`으로 둔다. 가정은 공유 문서에 남을 수 있지만, 개발로 넘기기 전에 확정되거나 사용자가 "가정인 채로 진행"을 결정해야 한다(결정 로그에 기록). 침묵은 동의가 아니다.
2. **커버리지 표가 다음 할 일을 정한다.** 필수 정보와 조건부 문서의 상태를 `확정 / 가정 / 미결 / 해당 없음(사유)`으로 적는다. 빈 칸마다 필요한 입력과 그것을 채울 수단을 하나씩 단다. 형식과 칸 목록은 [bundle-format](references/bundle-format.md).
3. **자기 몫은 바로 하고, 남의 몫은 묻는다.** 근거 기록, 결정 기록, 정책·흐름·IA 문서는 이 스킬이 한다. 아래 표의 일은 "다음은 <일>이고 `/<스킬>`이 맡습니다. 이어서 할까요?" 한 줄로 묻는다. 동의하면 같은 세션에서 그 스킬을 실행하고, 끝나면 결과를 묶음에 기록한 뒤 표로 돌아온다. 그 스킬의 확인 단계(grill의 공유 이해 확인, ac-draft의 덮어쓰기 확인)는 건너뛰지 않는다.

   | 빈 칸의 성격 | 맡는 스킬 | 돌아와서 기록할 것 |
   |---|---|---|
   | 방향·마일스톤이 없음 | `nara-roadmap` | 범위·비범위 후보 (합의된 것만 확정) |
   | 사용자만 정할 선택이 남음 (범위, 기준값, 우선순위, 예외 처리 방식) | `nara-grill` | `confirmed` 결정을 결정 로그로. `pending`은 미결 유지 |
   | 확정된 범위로 AC가 필요 | `nara-ac-draft` | `docs/requirements.md` 경로, AC 수, `[UNVERIFIED]` 수 |
   | 근거 원장이나 문서에 `<!-- src: -->` 마커가 달린 수치가 있음 | `nara-claim-audit` | 판정별 건수, `mismatch`·`mapping_failure`는 미결로 |
   | 화면 후보 또는 A/B 결정 | `nara-design-studio` / `nara-prototype` | 산출물 경로, 고른 안 |

   근거가 **비어 있는 것**과 근거가 **다른 쪽을 가리키는 것**은 다르게 다룬다. 비어 있으면(문제의 근거, 기준선 데이터, 이해관계자 의견이 없음) 고를 선택이 아니라 모르는 사실이므로 grill로 보내지 않고 Core Rule 4대로 사용자가 직접 구해 올 것으로 안내한다. 반대로 새 근거가 PRD의 문제 정의와 어긋나거나 다른 문제를 가리키면, 문제를 그대로 둘지 바꿀지 넓힐지는 지금 고를 수 있는 선택이다. 이때는 무엇이 어떻게 어긋나는지 설명하고 그 선택을 grill로 먼저 묻는다. 데이터를 기다리는 것보다 지금 내릴 수 있는 결정을 앞에 둔다.

4. **사용자가 직접 구해 와야 하는 것에서는 멈춘다.** 인터뷰, 데이터 요청, 이해관계자 승인처럼 사람이 해야 하는 일이면 무엇을 누구에게서 받아 와야 하는지 구체적으로 적고 멈춘다. 응답에서 이 경우를 "밖의 일" 같은 내부 용어로 부르지 않고 "다음은 ~를 받아 와 주셔야 합니다"처럼 할 일로 쓴다. 상태는 파일에 남으므로 다음 호출이 거기서 이어 간다.
5. **상태는 이 스킬만 바꾼다.** `prd.md` frontmatter의 `status: drafting | handed-off | measuring | closed`. 전이 조건은 [bundle-format](references/bundle-format.md#상태). `nara-now`는 이 값을 읽어 `drafting`일 때만 이 스킬을 추천한다. 폴더가 있다는 이유만으로 기획으로 돌아가지 않는다.
6. **덮어쓰지 않고 고친다.** 기존 묶음은 바뀐 절만 고친다. 고치기 전에 그 사실을 참조하는 곳(`docs/requirements.md`의 AC, 다른 묶음 문서)을 찾아 "영향받는 곳" 목록을 보여 주고 확인을 받는다. 커버리지 표에서 이미 `확정`인 칸을 `미결`이나 `가정`으로 내리는 것도 고치는 일이다. 내려야 할 이유를 찾으면 바로 바꾸지 말고 이유와 함께 묻는다. 새로 덧붙이는 것(열린 질문 추가, 관련 문서 링크 추가)은 확인 없이 해도 된다. 바뀐 결정은 지우지 않고 `대체됨: <날짜> <새 결정>` 표시를 남긴다.
7. **원문과 개인정보는 저장소 밖에 둔다.** 근거 원장에는 `참가자 A` 같은 익명 표기, 요약, 짧은 인용만 쓴다. 녹취·메모 원문, 실명, 연락처, 계정 식별자는 쓰지 않는다. 원문 위치는 사용자가 정한 저장소 밖 경로로만 가리킨다. 절차는 [evidence](references/evidence.md).
8. **요구사항은 복사하지 않고 옮긴다.** 기능 하나의 AC는 언제나 한 곳에만 있다: 개발 중이면 `docs/requirements.md`, 아니면 `docs/product/<slug>/requirements.md`. 절차는 [bundle-format](references/bundle-format.md#요구사항-이동).
9. **사내 기획 내용을 외부 검색에 넣지 않는다.** 시장·경쟁 정보가 필요하면 일반화한 질문으로만 찾고, 찾은 것은 근거 원장에 출처와 접근일을 붙여 넣는다.
10. **번호 참조를 쓰지 않고 뜻을 쓴다.** 기획 문서와 응답에 `(E-3 참고)`, `P-1`, `D-2`, `PROJ-123 참고`처럼 번호만 적지 않는다. 기획 문서는 배경을 모르는 사람이 읽으므로, 무엇을 가리키는지 문장으로 풀고 따라가야 하면 뜻이 적힌 링크로 쓴다. 영향 확인에 필요한 추적 키는 HTML 주석으로 숨긴다. 방법은 [bundle-format](references/bundle-format.md#참조-쓰는-법).
11. **사용자에게는 존댓말로, 기획 용어 없이 답한다.** 대화 응답은 합니다체나 해요체로 쓴다. 기획 문서 본문은 평서체(~다)로 쓴다. 응답에서 커버리지·미결·조건부 같은 이 스킬의 용어를 쓸 때는 처음 한 번 무슨 뜻인지 풀어 쓴다. 사용자는 기획을 처음 하는 사람일 수 있다.
12. **파생 문서는 조립만 한다.** 화면 설계서와 운영 개발 요청서는 묶음의 기준 정보를 읽는 사람에 맞게 다시 묶을 뿐 새 사실을 만들지 않는다. 재료가 모자라면 무엇을 먼저 채울지 알리고, 손으로 고친 파생 문서는 덮어쓰지 않는다. 방법은 [derived-docs](references/derived-docs.md).

## 인자 ($ARGUMENTS)

`nara-planning [<기능 한 줄> | <slug>] [<근거 파일 경로>...]`

플래그는 없다. 입력으로 할 일을 고른다.

- 인자 없음: 현재 브랜치 이름에서 slug를 찾아 그 묶음을 이어 간다. 못 찾으면 `drafting` 묶음 목록을 보여 주고 고르게 한다. 묶음이 없으면 무엇을 기획할지 한 질문만 하고 멈춘다.
- 새 기능 한 줄: 묶음 뼈대와 커버리지 표를 만든다.
- 기존 slug: 그 묶음을 이어 간다.
- 근거 파일(인터뷰 메모, 회의록, CSV): 근거 원장에 기록하고 표를 갱신한다.
- 파생 문서 요청("화면 설계서 만들어줘", "개발 요청서 써줘"): 재료를 확인하고 [derived-docs](references/derived-docs.md)대로 만든다.

## Procedure

1. **묶음 찾기**: 위 인자 규칙. `docs/product/<slug>/`가 있으면 `prd.md` frontmatter와 커버리지 표를 읽는다. 대화에 `nara-grill` Receipt나 다른 스킬 결과가 있으면 기록할 입력으로 잡는다.
2. **현재 동작 조사** (묶음을 새로 만들 때, 근거 원장에 코드 항목이 하나도 없을 때, 관련 코드가 바뀌었을 때): 기능이 건드릴 코드를 읽고 지금 어떻게 동작하는지와 기획이 부딪칠 위험을 근거 원장에 `코드` 항목으로 `경로:라인`과 함께 쓴다. 위험은 이런 것을 본다: 데이터가 저장되는지, 같은 요청이 두 번 오면 어떻게 되는지, 권한 검사가 어디 있는지, 실패와 재시도가 어떻게 처리되는지, 상태값이 무엇인지. 찾은 위험은 결정이 아니라 열린 질문이나 가정으로 올린다. 저장소에 관련 코드가 없으면 그 사실을 한 줄로 적는다.
3. **기록**: 이번 입력을 소유 파일에 쓴다. 근거는 `evidence.md`, 결정은 `prd.md` 결정 로그, 정책·흐름·IA는 조건부 문서. 조건부 문서는 [bundle-format](references/bundle-format.md#조건부-문서)의 조건이 맞고 확정된 규칙이나 코드로 확인한 현재 동작이 하나라도 있을 때 만든다. 조건은 맞는데 쓸 규칙이 없으면 표에 `미결 (조건 충족, 확정 규칙 없음)`, 조건이 안 맞으면 `해당 없음(사유)`. CSV에서 온 수치를 원장에 쓸 때는 `nara-claim-audit` 마커(`<!-- src: <file>.csv | <집계> -->`)를 같이 단다.
4. **정합성 점검**: 두 가지를 본다.
   - **같은 사실이 문서마다 다르게 적혔는지 대조한다.** PRD, 정책, 흐름, IA, 근거 원장, `docs/requirements.md`의 인수 기준, 그리고 코드에서 기준값(금액, 기간, 횟수), 기준의 대상(주문 금액인지 환불 금액인지 같은 것), 역할과 권한, 상태 이름과 전이, 화면 이름과 진입 경로를 하나씩 맞춰 본다. 예: 인수 기준은 "3만 원 이상 결제하면 쿠폰 지급", 정책은 "상품 금액 3만 원 이상이면 지급"이면 할인이나 배송비에 따라 결과가 달라지므로 다르다. 문서에 이미 있다고 적힌 화면이나 데이터가 코드에 없는 것도 어긋남이다. 어긋남을 찾으면 어느 쪽이 맞는지 고르지 않는다. 두 문장과 위치를 나란히 보여 주고, 어느 쪽이 맞는지를 사용자가 고를 결정으로 올린다. 이 결정은 다른 미결보다 먼저 묻는다. 어긋난 채로 쌓은 문서는 나중에 다 고쳐야 하기 때문이다.
   - **내용끼리 이어지는지 본다.** 목표의 KPI가 가치 제안의 "달라진 뒤"를 재는지, 범위의 기능이 가치 제안의 "어떻게"를 실현하는지, 정책 규칙마다 인수 기준이 있는지, 근거가 PRD의 문제 정의를 실제로 뒷받침하는지.

   어느 쪽이든 문서를 고치지 않고 미결 질문으로 표에 올린다. 대조한 항목 수와 찾은 어긋남 수를 receipt에 적는다. 찾은 것이 없으면 "어긋남 없음 (대조 N개)"라고 쓴다.
5. **표 갱신과 다음 하나**: 커버리지 표를 다시 계산하고 다음 할 일 하나를 고른다. 지금 사용자가 내릴 수 있는 결정이 있으면 그것을 먼저, 없으면 가장 앞의 빈 필수 칸. 자기 몫이면 이어서 하고, 남의 몫이면 Core Rule 3대로 묻고, 사용자가 구해 와야 하는 것이면 멈춘다.
6. **상태 전이**: 조건이 맞으면 `status`를 바꾸고 receipt에 적는다. `handed-off` 조건은 [bundle-format](references/bundle-format.md#상태).

## Output (receipt)

응답은 처음 기획하는 사람이 한 번에 읽을 수 있어야 한다. 순서는 결론 한 줄, 짧은 묶음들, trailing status, 마지막 한 줄의 질문이다.

```
첫 구매 쿠폰 기획을 갱신했습니다.

**먼저 정할 것**
- 쿠폰 지급 기준 3만 원이 결제 금액인지 상품 금액인지 문서마다 다릅니다.
  - 정책: "상품 금액 3만 원 이상"
  - 인수 기준: "3만 원 이상 결제"

**이번에 한 일**
- 지금 쿠폰 발급 코드를 읽고 동작 3가지를 근거로 남겼습니다.
- 고객 인터뷰 2건을 정리했습니다. 참가자 이름과 연락처는 옮기지 않았습니다.
- 화면 설계서 `screens.md`를 만들었습니다.

**진행 상황**
꼭 필요한 정보 6개 중 4개 확정, 1개 가정, 1개 미정입니다.

(trailing status 블록)

다음은 위 지급 기준을 정하는 일이고 `/nara-grill`이 맡습니다. 이어서 할까요?
```

- 한 줄에 사실 하나만 쓴다. `·`로 여러 사실을 잇지 않는다.
- 괄호 안에 괄호를 넣지 않는다. 용어 설명은 괄호가 아니라 그 용어가 처음 나온 줄 다음에 짧은 문장으로 쓰거나, 용어 대신 뜻을 쓴다("커버리지 1/6" 대신 "꼭 필요한 정보 6개 중 1개").
- 묶음 제목은 굵은 글씨 한 줄로 쓰고, 내용이 없는 묶음은 쓰지 않는다. "먼저 정할 것"은 문서끼리 어긋남이나 지금 고를 결정이 있을 때만 맨 앞에 둔다.
- 파일 경로는 사용자가 열어 볼 파일만 쓴다.

## Trailing status (필수)

```
bundle: docs/product/<slug>/ | none (<사유>)
status: drafting | handed-off | measuring | closed
coverage: required r/R confirmed · assumed a · open o · n/a x   # 필수 정보만 센다
claims: body N (sourced s / assumed a)
consistency: checked N · conflicts c
decisions: N (sourced s / unsourced u)
next: <스킬 이름 또는 사용자가 준비할 것 하나> | done
```

`unsourced`가 1 이상이면 그 결정은 본문에 쓰지 않은 것이다. `open`이 1 이상이면 "기획 완료"라고 보고하지 않는다. `next`는 항상 하나다.

status 블록 다음 줄이 응답의 마지막 줄이다. 남의 몫이면 "이어서 할까요?", 사용자가 준비할 것이면 무엇을 누구에게서 받아 오면 되는지 한 줄. 그 뒤에 다른 문장을 붙이지 않는다.

## Error Handling (if-then)

| 트리거 | 대응 |
|---|---|
| 기획할 대상도 묶음도 없음 | 무엇을 기획할지 한 질문만 하고 멈춘다 |
| 방향 자체가 없음 (무엇을 할지 모름) | 묶음을 만들지 않고 `nara-roadmap`을 묻는다 |
| 사용자가 수치·정책·일정을 채워 달라 함 | 근거가 없으면 `[가정]` 라벨로만 쓰고 표 상태는 `가정`. 기준선처럼 측정해야 아는 값은 가정으로도 채우지 않고 `미결` |
| 근거 파일에 실명·연락처·계정이 있음 | 원장에 옮기지 않는다. `참가자 A`처럼 익명으로 바꿔 요약하고 원문은 저장소 밖에 두라고 안내 |
| 원문 파일이 저장소 안에 있고 git이 추적 중 | 기록 전에 멈추고 알린다. 지우거나 이력을 고치는 일은 하지 않는다 |
| 바꾸려는 결정에 인수 기준이 걸려 있음 | 걸린 인수 기준을 문장으로 보이고 확인 전까지 쓰지 않는다 |
| `docs/requirements.md`의 주인이 불분명하거나 미커밋 변경이 있음 | 요구사항을 옮기지 않고 멈춘다 |
| 사용자가 다른 스킬로 이어 가기를 거절 | 표에 미결로 남기고 receipt를 끝낸다 |
| 파일을 쓸 수 없음 | 같은 내용을 대화로 내고 `bundle: none (<사유>)` |
